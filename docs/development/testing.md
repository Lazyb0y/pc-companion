# Testing

## Unit tests

```
dotnet test --solution PCCompanion.slnx -c Debug -p:Platform=x64
```

- xUnit v3 on Microsoft.Testing.Platform, which `global.json` selects for `dotnet test`. Test projects go in `tests/` and are included in the solution.
- Test doubles and helpers that more than one test project needs go in `tests/PCCompanion.Testing`, not into each project, such as `RecordingLogger<T>`, which keeps every log entry, `ManualTimeProvider`, a clock and timers that move only when a test advances them, `TemporaryFolder`, an empty folder deleted when the test ends, `FakeHostCommands`, which records the host's commands, and `TestJson.Section`, a settings section from JSON text.
- `PCCompanion.Architecture.Tests` checks that every project is in the solution, that project references have no cycles, and that they follow the [dependency rules](../architecture/overview.md#dependencies).

## Checks before a pull request

```
powershell -ExecutionPolicy Bypass -File scripts\verify.ps1
```

- Builds Debug and Release for x64 and ARM64 and fails on any warning, runs the tests of each build, and checks the lock files with a locked restore, as CI does. It lists lock files the build changed, which belong in the commit.
- `-Quick` builds only Debug x64; `-Installer` also builds the installers.

## Testing in Windows Sandbox

```
powershell -ExecutionPolicy Bypass -File scripts\sandbox-test.ps1 -Checks HotCorners
```

- Builds the installer for this PC's architecture and runs groups of checks in Windows Sandbox, so this PC isn't changed. The Sandbox window closes when the checks finish.
- The Sandbox has networking only when a group needs it, as SystemMeters does for real network traffic. Such a group says so with a `# Networking: on` line at its top: `sandbox-test.ps1` then turns networking on in the Sandbox's configuration, and `run-checks.ps1` turns every network adapter off before Smoke and on only during such groups. While the Sandbox has networking, the hosts file points `api.github.com` at the Sandbox itself, and the groups turn the update check off, so GitHub gets nothing. The report says which groups had the network.
- `-Checks` runs only the groups named, such as `-Checks HotCorners` or `-Checks Setup,Dialogs`. Smoke always runs first, and the groups run in the order below, whatever the order given. Without `-Checks`, every group runs.
- Each group is a script in `scripts\sandbox\groups`, which `scripts\sandbox\run-checks.ps1` runs with the helpers of `common.ps1`.
- Each group starts with nothing of PC Companion running and without the user's settings and logs, and with PC Companion installed just for the current user, or not installed for Smoke, RunAsAdmin and Dialogs, so it doesn't depend on what another group left. Once a group is done, its logs are checked for errors and for the user name.
- After each group, its logs are checked: they have no errors, don't show the user name, and have no warning that a feature held the host's UI thread for 100 ms or more. The host warns from 50 ms, but the Sandbox is slower than a PC and a first run of a path can come close to that, so the report notes shorter holds instead. It also notes one known hold, the host adding its tray icon again after Explorer restarts (`TaskbarCreated`), whatever its length.
- Writes the report to `TestResults\sandbox`, with a folder for each group that holds its screenshots and logs, and exits with an error when a check fails. The report and the end of the output list each group's checks, failures and time.
- Needs the Windows Sandbox feature; only one Sandbox can run at a time. `-NoBuild` uses the installer already built.
- `-Msi <path>` checks that installer instead of building one, such as an installer downloaded from a draft release; it must be for this PC's architecture. The Sandbox gets a copy without the mark Windows puts on downloaded files, so the checks don't stop at Windows' security warnings.
- Windows Sandbox starts Smart App Control in evaluation mode, where, with networking off, every install waits about two minutes for its check before Windows Installer goes on. So the checks turn it off before they install anything. `-SmartAppControl Evaluation` leaves it as the Sandbox starts it, and `-SmartAppControl On` turns it on: PC Companion then installs, but an unsigned build is blocked when it starts. For an unsigned installer, `sandbox-test.ps1` warns before it starts the Sandbox; Smoke reports the block with Windows' reason, and the other groups don't run. The report says which was used.
- A group that needs a test SFTP server, as RemoteFolders does, says so with a `# Needs: OpenSSH` line at its top. `sandbox-test.ps1` then downloads OpenSSH for Windows, a release pinned in the script, from GitHub the first time, checks its SHA-256 and keeps it in `TestResults\openssh`. The Sandbox gets a read-only copy and still has no networking.
- Keep the Sandbox window visible and the mouse outside it while the checks run. A minimized Sandbox draws nothing, so its screenshots come out blank (the report notes this), and the Hot Corners & Edges checks can't move the pointer inside it.

### What to run for a change

- A feature: its group, such as `-Checks HotCorners`. Smoke runs with it.
- The settings app's window, navigation or pages, the tray icon or **Start with Windows**: App.
- Strings, translations or right-to-left layout: Languages, with the group of the feature whose page changed.
- Logging: Logging.
- The update check, its notification or banner: Updates.
- The installer, or what setup runs, such as the host's `--exit` and `--remove-data`: Setup and Dialogs, and RemoteFolders when it changes what uninstalling removes of Remote Folders.
- Elevation, the elevated helper or all-users installs: RunAsAdmin and Setup, and RemoteFolders for the helper's `remove-all-remote-folders`.
- Code changes also need `verify.ps1`, with `-Installer` only when the installer changes; CI builds the installers.
- Every group, without `-Checks`: after a few big changes, and before a pull request or a release.

### Adding a group

- A feature with runtime behavior worth checking gets a group: `scripts\sandbox\groups\<Feature>.ps1`, and an entry in `$startStates` in `run-checks.ps1` with what it starts from. Groups that remove PC Companion or install it for all users go last.
- A group opens what it needs, such as the settings app, and doesn't rely on another group. Helpers that more than one group uses go in `common.ps1`.
- Checks of where the settings app puts keyboard focus read it with `Get-AppFocusedName`, which brings the settings window to the front first. When the settings app closes while a notification is on the screen, such as one an earlier group left, the notification takes the front and the keyboard focus and keeps them while there's no input, as in the Sandbox, and no other window can take the front from it. So the helper first sends a notification that has the front to Notification Center, as its close button does, and the report notes it.
- A group that needs the network starts with a `# Networking: on` line, and turns the update check off in the settings it writes. Other groups keep networking off.
- A group that needs a test SFTP server starts with a `# Needs: OpenSSH` line, and sets up the server in the Sandbox from `C:\Test\openssh`.
- A group opens a tray menu at `$menuX`, `$menuY` from `common.ps1`, in the upper left of the screen. Windows shows notifications in the bottom-right corner and keeps them there while there's no input, as in the Sandbox, so one that an earlier check left can cover a menu there and take its click.
- UI Automation reads a tray menu's items as empty when no window has the front. A posted message, unlike a click on the icon, doesn't let the host take the front, and a notification that has it keeps it until it leaves, after which nothing has it. So before DisplayProfiles opens its tray menu, `Set-HostFront` sends a notification in front to Notification Center, as `Get-AppFocusedName` does, and puts the host's window in front; the report notes how many notifications went.

## Testing tasks

Every feature has one testing task on GitHub: an issue for the maintainer to test by hand what unit tests and Windows Sandbox can't check, such as real hardware, several displays and scales, UAC on, Windows 10, ARM64, Narrator and other programs. It's titled "Test <feature> by hand" and has the feature's area label. Parts of the app that aren't one feature, such as the tray icon, the feature icons or Windows 10 and ARM64, can have a testing task of their own, kept the same way.

A testing task holds:

- **What's covered:** what the unit tests and the feature's Sandbox group check, and how the Sandbox differs from a real PC.
- **Test scenarios:** a checkbox for each, from the "By hand" part of the Testing section of the feature's spec, under a bold heading for each part of the feature when there are many.
- **Acceptance criteria:** what must hold for the feature to pass, from its spec.
- **Reporting:** a comment with the Windows version, the architecture and the hardware used, and anything that didn't match.
- **Changes to retest:** a dated entry for each change to the feature since the task was written, or "None yet."
- **Related:** the spec, and the issues and pull requests that built or changed the feature.

The lifecycle:

1. **A new feature** gets its testing task in the task that finishes it, linked in the task report and the pull request.
2. **A change to a feature,** its behavior or its code, a fix included, updates the feature's existing testing task. Search the issues, open and closed, for it, and never create a second one. Add a dated entry under "Changes to retest" with what changed, in which issue or pull request, the areas it affects, new test scenarios and the regression checks that apply. Add checkboxes for new checks, untick those that need running again, and comment asking for a retest. A closed testing task is reopened first. A change that touches several features, or a part of the app with its own testing task, updates each of their tasks.
3. **The maintainer runs the checks,** comments with the results, and closes the task once everything passes. Feature issues close when their work is done; testing tasks stay open until then.

Creating, editing, reopening and commenting on testing tasks needs no separate request from the maintainer (2026-11-24); every other change on GitHub still does.
